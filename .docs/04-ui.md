# Phase 4 — The reading UI

The website stops being a mirror of the email and becomes the thing itself.

**Done when:** reading the briefing on an iPhone is better than reading the old
email was.

---

## 4.1 What changed about the requirements

The old website was secondary. The email was where you read, and the site had
to be a passable fallback, so it inherited the email's constraints: a flat
column, footnotes as a numbered list at the bottom, styling that echoed what
survives an email client.

Now it's the only surface, and it has one target: **an iPhone, in standalone
mode, first thing in the morning.** That removes every email constraint and
adds new ones.

| Freed from | Newly required |
|---|---|
| Table layouts, inline styles | Safe-area insets — no browser chrome to protect the notch or home indicator |
| No JS | Tap targets ≥ 44px |
| Fixed light palette | Dark mode — it's 6am |
| ~600px fixed width | Real responsive layout |
| Footnotes far from the word | Footnotes *at* the word |

## 4.2 The reading problem worth solving

The single biggest improvement available: **stop making the reader scroll to
the bottom to find out what a word means.**

Every article has 8–12 bold words with German-only explanations. In the email
they were superscript numbers pointing at a list under the article. On a phone
that means scroll down, read, lose your place, scroll back. Every time. Eight
to twelve times per article, five articles a day.

Instead: **tap the bold word, the explanation appears in place.** A bottom
sheet on mobile, a popover on desktop. Dismiss and you're exactly where you
were.

This is why `lib/footnotes.ts` is worth keeping (Phase 2): `buildFootnotes`
already pairs each `**word**` with its explanation and numbers them by order of
appearance in the *text*, so a word the model highlighted but didn't explain
stays bold with no dangling reference. That logic drives the tappable spans
directly.

Keep the numbered list at the end too, collapsed. It's a decent review tool
once you've read the piece.

## 4.3 Structure

Four routes.

**`/` — today.** The five articles. Above them, the date and a compact category
rail so you can jump straight to Gaming if that's your mood. The German title
leads; the English title is secondary — you're here to read German.

**`/archiv/[datum]` — one past day.** Same reading view. (Rename from
`/archive`: the UI is German throughout, and the old mix of a German interface
on English routes was always slightly odd.)

**`/archiv` — the archive index.** Grouped by month, each day showing its five
German titles so you can find the piece you half-remember. The old index was a
bare list of dates, which is unusable past about two weeks.

**`/vokabeln` — the vocabulary list.** New. `vocabulary` has been accumulating
words with `times_used_total` and `last_used_date` since day one and nothing
has ever displayed it. Sort by least-seen, show the article each word came
from. This is the highest-value new page in the app and it needs no new data.

## 4.4 Design direction

A proposal, not a spec — worth reacting to before anyone writes CSS.

**Typography first.** This is a reading app for dense German prose. Body text
around 19–20px with generous line height. A serif for article bodies reads
noticeably better at length than the current system sans; system UI font for
chrome. One column, ~68 characters, centred.

**Quiet chrome.** No shadows, no cards, no gradients. Rules and whitespace to
separate articles. The content is five news articles — the UI should get out of
the way.

**Colour carries meaning, once.** One accent, used for the five category
labels and for the tappable bold words. The bold words need to read as
*interactive* without looking like links in the middle of German prose — a
subtle dotted underline in the accent colour, not blue text.

**Dark mode is not optional.** Respect `prefers-color-scheme`. Define the light
palette on `:root`, override only the tokens under a `prefers-color-scheme:
dark` block, and give `body` an explicit background.

**Safe areas.** In standalone mode there is no browser chrome. Set
`viewport-fit=cover` and pad with `env(safe-area-inset-top)` /
`env(safe-area-inset-bottom)`, or the first line sits under the notch and the
last sits under the home indicator.

Keep it hand-written CSS in `app/globals.css`, as now. The app is four pages;
a framework would be more configuration than code.

## 4.5 Components

| Component | Fate |
|---|---|
| `SiteHeader` | Rewrite — four routes now, and it's the standalone app's only navigation |
| `ArticleView` | Rewrite — this is where tap-to-read footnotes live |
| `AutoRefresh` | **Delete.** A 5-minute `location.reload()` in a standalone PWA will reload the page mid-sentence. Push tells you when there's something new |
| `ManualTrigger` | Keep, move to a settings page. Not on the reading surface |
| `FootnoteSheet` | New — the bottom sheet / popover |
| `CategoryRail` | New — jump-to-category |
| `PushToggle` | New, Phase 5 |

### On deleting `AutoRefresh`

Worth being explicit, because removing it looks like a regression. It exists
because the page is ISR with `revalidate = 300` and there was no other way to
learn a briefing had landed. In a standalone PWA, iOS keeps the page alive in
the background for a long time — a timed reload will fire while you're reading.
Phase 5 replaces it properly: the push handler can refresh the cached page, and
tapping the notification opens today's briefing fresh.

Keep `revalidate = 300` on the page, and keep the `revalidate` route the
briefing run pings (Phase 2) — that's what makes the content there the instant
the notification arrives.

## 4.6 Empty and error states

The empty state is now a monitor (Phase 3.5). It must answer "is the app
broken, or is it just early?"

- **Before the run, today's missing:** "Das heutige Briefing wird gerade
  erstellt." — with the expected time.
- **Well after the run, today's missing:** say so plainly and show the last
  successful date: "Letztes Briefing: Montag, 13. September." That's the signal
  something broke.
- **Database unreachable:** `lib/queries.ts` swallows errors to an empty array,
  so this is indistinguishable from "no articles" at the page level. Either
  surface the distinction or accept it — but decide deliberately rather than
  discovering it during an outage.

Read `briefing_runs` for today's `status` to tell these apart; it already
records `pending`, `completed` and `failed` with an error message.

## 4.7 Acceptance criteria

- [ ] Reads well on an iPhone in standalone mode, including notch and home indicator
- [ ] Tapping a bold word shows its explanation without losing reading position
- [ ] Dark mode follows the system
- [ ] `/vokabeln` lists accumulated vocabulary, least-seen first
- [ ] Archive index is navigable past 50+ days
- [ ] Empty state distinguishes "not yet" from "something broke"
- [ ] `AutoRefresh` deleted
- [ ] No horizontal scroll at 390px
